# ADR 0001 — 小红书的抓取范围

- **状态**：未决 ⚠️
- **提出**：2026-08-07（仓库整理时发现文档与代码互相矛盾）
- **决定人**：项目所有者

## 矛盾

`bite/CLAUDE.md` 曾白纸黑字写着（2026-05-19 对齐的 v1 决策）：

> v1 外部数据源仅小红书，且仅 **纯文本粘贴路径**（**不爬** xhs 服务器）

而代码在做的事恰好相反：

| 位置 | 行为 |
| --- | --- |
| `bite/src/lib/places/xhs.ts` | 定义伪装的桌面 Chrome User-Agent + `zh-CN` Accept-Language |
| 同上 | 直接 `fetch` xiaohongshu.com 的分享页 |
| 同上 | 正则提取 `window.__INITIAL_STATE__`，取出正文、`tagList`、**作者昵称**、**作者 IP 属地**、**前 12 条评论（含评论者昵称）** |
| `bite/src/lib/storage/mirror-photos.ts` | 把帖子图片下载后转存进自有 Supabase Storage bucket |

文档是下一个人（和下一个 AI agent）会相信的那一份，所以这个矛盾比任一选项本身更糟。

## 附带事实：搜索引擎路线是死的（2026-08-10 实测）

小红书 robots.txt：`User-agent: Googlebot` → `Disallow: /`（只放行一个世界杯专题）；
末尾 `User-agent: *` → `Disallow: /`。所以：

- Google / Serper 上 `site:xiaohongshu.com <店名>` 结构性为空 ——
  `searchXhsPosts()` 这个功能不可能有结果，不是缺 key。
- 网页版搜索页也要求登录（`/web/search/result` 会 302 到首页并丢掉关键词）。

也就是说，**抓取分享链接是目前唯一能从小红书拿到内容的路径** —— 这反过来加重了
下面这个取舍的分量：砍掉抓取就等于砍掉小红书这个数据源，没有折中的「合规搜索」替代品。

## 三重暴露

1. **平台条款**：自动化采集违反小红书的服务条款。
2. **版权**：转存第三方图片与正文到自有存储。
3. **个人数据**：存储了具名第三方的评论内容、昵称和 IP 属地——这些人既不是 Bite 的用户，也从未同意。

## 附带发现：一个可达的 SSRF

`scrapeXhsUrl` 用 `redirect: "follow"`，而 `xhslink.com` 是攻击者可控的短链跳转器。
跳转后**没有 host 复检、没有私网 IP 防护**，且抓到的内容会回显到确认页。
任意登录用户可达。无论下面选哪个方案，这条都建议单独修（跳转后校验最终 host 在
小红书域名白名单内，并拒绝解析到私网段的地址）。

## 选项

**(a) 保留抓取，砍掉个人数据采集** —— 继续抓正文/标题/标签/图片，但不再提取
作者昵称、作者 IP 属地、评论区内容。保住大部分体验（AI 抽取主要靠正文），
去掉三重暴露里最实在的那一维。

**(b) 退回纯文本粘贴** —— 与最初决策一致，合规最干净。代价是体验明显倒退：
用户得自己打开小红书、复制正文、再粘回来，且拿不到图片。

**(c) 接受现状，只把文档改成真话** —— 已经在 `CLAUDE.md` 里做了（如实描述 + 指向本 ADR）。
个人项目、熟人使用、量极小，风险实际很低。但这个选择应该是**明知故犯**，不是默认漂移。

## 建议

倾向 **(a)**：评论区和 IP 属地对「帮我决定今晚吃哪家」的价值有限，但它们是三条暴露里
唯一涉及**具名第三方个人数据**的一条。砍掉它成本很小，收益是把问题从「个人数据合规」
降级成「ToS 灰区」——后者对一个自用工具是可接受的。

无论选哪个，SSRF 那条都该修。

## 后果

选定后必须同步更新 `bite/CLAUDE.md` 的对应段落，并把本文件状态改为「已决」。
